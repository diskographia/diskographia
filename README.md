# disk64.zip: Dисkographия

Платформа для авторов. Люди складывают сюда работы, собирают из них выставки и подборки, отмечают друг друга откликом. Всё содержимое живёт предметами одного вида данных, интерфейс собран одним модулем с пятью экранами.

```
apps/client      Next.js, интерфейс
apps/server      NestJS, API
packages/shared  типы и схемы проверки, общие для клиента и сервера
deploy           образец конфига caddy и скрипты выкатки
tools            сборка спрайтов и значка из исходников, промер макетов в tools/measure
docs             рабочие записи, в репозиторий не входят
```

## Из чего состоит платформа

**Предмет** это единица всего. Четыре вида:

| Вид | Что это | Контейнер |
|---|---|---|
| `content` | работа, статья, запись | нет |
| `product` | товар: цена или обмен, контакты | нет |
| `event` | ивент: даты, адрес, анонс, расписание, заявки | да |
| `capsule` | капсула: подборка чего угодно, без дат | да |

Контейнеры это `event` и `capsule`, внутрь них кладётся что угодно, включая другие контейнеры: подборка главной это капсула, в которой лежит ивент. Круги и глубину больше десяти уровней запрещает база. Один и тот же предмет может лежать в нескольких контейнерах сразу. Чужой предмет в ивенте ждёт согласия автора, в капсулу кладётся свободно.

**Видимость** идёт лестницей: `draft`, `private`, `unlisted`, `public`. Черновик и приватный отдают 404 всем, кроме владельца и соавторов с правом правки, и по адресу, и по id, и в медиа, и внутри контейнера: владелец капсулы чужой черновик в ней тоже не видит. Ступенька «по ссылке» намеренно открыта любому, кто знает адрес, отдельного ключа нет.

**Отклик** это вес автора, накопленная экспа. Считается автору предмета, а не владельцу: колонки `entities.author_id` и `entities.owner_id` разведены. Передать можно владение, авторство остаётся у того, кто сделал.

**Адреса** строятся из одного файла `apps/client/src/routes.ts`, ссылок, собранных строкой на месте, в проекте нет.

| Адрес | Что показывает |
|---|---|
| `/` | главная: подборка либо экран идущего глобального ивента |
| `/@ник` | учётка: инвентарь, отклик, о себе |
| `/@ник/слаг` | предмет |
| `/@ник/слаг/pravka` | правка предмета, тем у кого есть право |
| `/sozdat` | создание предмета |
| `/moi` | свои предметы, включая черновики |
| `/poisk` | поиск: полнотекстовый, нечёткий, фасеты по тегам |
| `/zayavki` | свои заявки на ивенты |
| `/korzina` | своё удалённое, возврат |
| `/uvedomleniya` | уведомления |
| `/nastroiki` | настройки уведомлений, выход |
| `/pravka` | правка своей учётки |
| `/svodka` | сводка, только учётке платформы |
| `/moderaciya` | чужие предметы, только учётке платформы |
| `/vhod` | вход |

**Вход** это кука `diskographia_session` с токеном, недоступная скриптам. Сервер читает её сам, поэтому браузер ходит в `/api` напрямую через caddy. В разработке caddy нет, и тот же путь держит прослойка `apps/client/src/app/api/[...path]/route.ts`. Серверные запросы клиента идут по `API_INTERNAL_URL`, в стенде это адрес контейнера сервера. Сессии лежат в таблице `sessions`: выход и смена пароля гасят их на сервере, а не только стирают куку. Срок сессии `JWT_TTL` скользящий: когда прошла половина, сервер на запросе из браузера продлевает её на полный срок и обновляет куку, а вошедший браузер раз в час сам стучится в `/api/auth/me`, чтобы продление случилось даже без других запросов. Кто заходит хотя бы раз за срок, не разлогинивается; обновления сайта сессии не трогают.

## Интерфейс

Весь сайт живёт в одном модуле с пятью экранами: слева большой читающий, справа сверху показ, под ним два маленьких и правый высокий. Что не влезло в экран, не режется и не прокручивается: содержимое разливается по страницам шириной в экран и листается стрелкой в углу по кругу. Прокрутка есть только у левого экрана, где читают статью, и вынесена на ребро модуля отдельной полосой со шагом в строку.

Слева на рейке четыре зелёные клавиши: домой, назад и две по месту. Чёрные ручки сверху и снизу листают соседей, они появляются только внутри контейнера и только когда что-то выбрано. Уход со страницы с незаконченной правкой спрашивает про сохранение.

Слева сверху дека плеера: динамик открывает сет и пульсирует на ходу, рядом полоса перемотки, дальше табло с названием, столбиком клавиши «назад, пауза, вперёд» и счётчик времени.

Настройка главной живёт на самой главной: учётка платформы видит кнопку «настроить главную», модуль переключается в режим настройки. Там три полки, в которые кладутся уже готовые предметы, создавать оттуда нельзя:

- **подборка** это лента главной, когда глобального ивента нет
- **витрина** это мерч в правом верхнем экране
- **манифест** это одна статья вида `content`, она открывается модалкой по нажатию на летающий логотип, видимость переключается там же

Пока идёт глобальный ивент, главная это он. Держится он на галке «глобальный» в правке ивента и на его датах: с времени анонса до конца плюс «сколько дней висит после окончания». Управление ивентом собрано там же на главной: программа, заявки, правка, очереди показа.

## Разработка

Нужны Node 24, pnpm 11 и PostgreSQL 18.

```bash
pnpm install
cp apps/server/.env.example apps/server/.env      # заполнить DATABASE_URL, JWT_SECRET, PLATFORM_PASSWORD
cp apps/client/.env.example apps/client/.env.local

pnpm db:migrate
pnpm seed:admin

pnpm --filter @diskographia/server dev            # порт 4000
pnpm --filter @diskographia/client dev            # порт 3000
```

Сквозные команды из корня: `pnpm typecheck`, `pnpm lint`, `pnpm build`, `pnpm db:migrate`, `pnpm seed:admin`, `pnpm seed:clean`, `pnpm assets`.

`pnpm assets` пересобирает спрайты, шрифты и значок вкладки из папки с исходниками в `apps/client/public` и `apps/client/src/app`. Исходники в репозиторий не входят, готовые файлы входят, так что без них проект собирается.

## Ветки и проверки

- `main` это то, что стоит на боевом сервере
- работа идёт в отдельных ветках, вливается через pull request
- на каждый pull request GitHub Actions гоняет типы, линтер, обе сборки, миграции на чистой базе и разбор `docker-compose.yml`
- на `main` он же собирает боевые образы и кладёт их в `ghcr.io/diskographia/diskographia-server` и `diskographia-client` с тегами `latest` и `sha-<коммит>`. Адреса клиента вшиваются в образ при сборке: их боевые значения задаются переменными репозитория (settings, variables, `NEXT_PUBLIC_*`), без них берутся значения из `.env.production.example`
- **пуш ничего не выкатывает.** Боевой сайт меняется только руками, командой по ssh: сервер тянет готовый образ

## Как это стоит на сервере

```
браузер ──> caddy на самой машине ──┬──> 127.0.0.1:3000  клиент, контейнер
                                    ├──> 127.0.0.1:4000  сервер, контейнер ──> postgres, контейнер
                                    └──> папка на диске   загруженные файлы, отдельное имя
```

В докере крутятся только клиент, сервер и postgres, наружу они не смотрят вообще: порты слушаются на `127.0.0.1`. Домены, сертификаты и раздачу файлов держит caddy на самой машине.

Репозитория на сервере нет и ничего там не собирается: образы приходят готовыми из `ghcr.io`. На сервере лежит только папка стенда, `/srv/diskographia`: `docker-compose.yml`, `.env.production`, `deploy/` со скриптами, рядом `uploads` и `backups`.

База живёт в томе докера `postgres`, загруженные файлы обычной папкой на диске, чтобы caddy отдавал их напрямую, минуя докер и node. И то и другое переживает пересборку.

Файлы стоят на отдельном имени: так загруженный кем-то файл не окажется на одном имени с сайтом. Раскладка на диске от даты и хеша: `2026/09/ab/<sha256>.jpg`, превью рядом в `derivatives`. Одинаковые файлы дедуплицируются по хешу: путь уже лежащего файла берётся из базы, вторая копия не пишется. Тип файла определяется по содержимому, а не по заголовку запроса.

### Сервер с нуля

Ubuntu 24.04, пользователь с sudo, caddy уже стоит на машине.

```bash
# докер
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER && newgrp docker

# папка стенда и папка под загруженные файлы, её будет отдавать caddy
sudo mkdir -p /srv/diskographia/uploads
sudo chown -R "$USER" /srv/diskographia
```

С рабочей машины в папку стенда копируются три вещи из репозитория, они меняются редко:

```bash
scp -r docker-compose.yml .env.production.example deploy пользователь@адрес:/srv/diskographia/
ssh пользователь@адрес 'cd /srv/diskographia && chmod +x deploy/*.sh && cp -n .env.production.example .env.production'
```

Если репозиторий на GitHub закрытый, пакеты в `ghcr.io` тоже закрытые, и докеру на сервере нужен вход: токен GitHub с правом `read:packages`, один раз `docker login ghcr.io -u <логин>` и токен вместо пароля. У открытого репозитория пакеты тянутся без входа.

В `.env.production` заполнить:

- `POSTGRES_PASSWORD` и тот же пароль внутри `DATABASE_URL`
- `JWT_SECRET`, получить: `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`
- `PLATFORM_EMAIL` и `PLATFORM_PASSWORD`, это учётка платформы
- домены в `CLIENT_ORIGINS`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_UPLOADS_URL`
- `UPLOADS_HOST_DIR`, папку из шага выше
- `SERVER_PORT` и `CLIENT_PORT`, если 4000 и 3000 на машине заняты
- `IMAGE_TAG` обычно `latest`, скрипт выкатки меняет его сам

Домены: основной и отдельный для файлов, оба A-записью на адрес сервера.

```bash
./deploy/first-run.sh
```

Скрипт стянет образы, поднимет базу, прогонит миграции и заведёт учётку платформы. После этого в базе только она и три пустых контейнера: подборка, витрина, манифест. Всё остальное заводится руками через интерфейс.

### Переезд с сервера, где стенд уже стоит из репозитория

Данные трогать не нужно: база в томе докера, файлы в `UPLOADS_HOST_DIR`. Единственная ловушка: имя тома складывается из имени папки, в которой лежит `docker-compose.yml` (`diskographia_postgres`). Поэтому новые `docker-compose.yml` и `deploy/` кладутся в ту же папку, где стенд стоит сейчас, поверх старых, `.env.production` остаётся, в него дописывается `IMAGE_PREFIX` и `IMAGE_TAG` из образца. Дальше обычная выкатка: `./deploy/deploy.sh`. Клон репозитория после этого можно удалить, оставив в папке только `docker-compose.yml`, `.env.production`, `deploy/`, `uploads` и `backups`, но саму папку не переименовывать. Если очень хочется переехать в `/srv/diskographia`, сначала `docker compose down`, потом в новой папке `COMPOSE_PROJECT_NAME=<имя старой папки>` в `.env.production`, тогда том найдётся.

### Caddy

Образец лежит в `deploy/Caddyfile`: `/api/*` уходит на сервер, всё остальное на клиент, отдельное имя раздаёт папку с файлами со своими заголовками безопасности. Домены и путь к папке в нём надо поменять на свои.

```bash
sudo cp deploy/Caddyfile /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Сертификаты caddy выпускает и продлевает сам. Если они приходят снаружи или выпускаются через dns-испытание, в блок домена добавляется свой `tls`, остальная часть конфига не меняется.

Файлы в папку пишет контейнер сервера от рута, права выходят `644` на файлы и `755` на папки, поэтому caddy читает их без дополнительной настройки. Всё, кроме картинок и медиа, caddy отдаёт как скачивание: чужой html или svg в браузере не откроется.

Правки в `Caddyfile` нужны только когда меняются домены или порты. Обычная выкатка кода caddy не трогает.

### Обычная выкатка

Сначала коммит попадает в `main` и GitHub Actions докладывает, что образы собраны (вкладка Actions, задача «образы в ghcr.io»). Потом:

```bash
ssh пользователь@адрес
cd /srv/diskographia
./deploy/deploy.sh                    # свежий latest
./deploy/deploy.sh sha-<коммит>       # ровно этот коммит
```

Что происходит по шагам: тянутся образы, снимается копия базы и файлов, прогоняются миграции, контейнеры переключаются, скрипт ждёт ответа `/api/health` по локальному порту. Пока тянутся образы, работает старая версия. Простой равен перезапуску контейнеров, это секунды. Если новая версия не ответила за полторы минуты, скрипт печатает команды логов и отката, а старые образы подчищает сам.

Если поменялись сами `docker-compose.yml` или скрипты в `deploy/`, их нужно скопировать на сервер заново той же командой `scp`, что при первой установке.

### Откат

```bash
./deploy/deploy.sh sha-<прошлый коммит>
```

Тег пишется в `IMAGE_TAG` в `.env.production`, следующая выкатка без аргумента вернёт `latest`. В теге полный хеш коммита, `sha-` и сорок знаков: список собранных тегов виден на GitHub в разделе Packages, хеш нужного коммита даёт `git rev-parse <коммит>`.

Миграции идут только вперёд, откат кода схему не возвращает. Поэтому опасны только те, что удаляют или переименовывают. Правило: сначала добавили колонку и выкатили код, который умеет и по-старому и по-новому, и только следующей выкаткой убрали старую. Тогда откат кода всегда безопасен.

## Обслуживание

### Что проверить после выкатки

```bash
docker compose --env-file .env.production ps          # все контейнеры healthy
curl -fsS http://127.0.0.1:4000/api/health            # {"ok":true}, изнутри машины
curl -fsS https://ваш-домен/api/health                # то же снаружи, через caddy
```

Раз в неделю: место на диске (`df -h`, `docker system df`) и свежесть копий в `backups`. Сертификаты caddy держит сам, следить за ними не нужно.

### Если сайт не открывается

Одна команда делит проблему пополам: `curl http://127.0.0.1:4000/api/health` изнутри машины. Отвечает, значит контейнеры живы и дело в caddy. Не отвечает, значит дело в контейнерах.

```bash
docker compose --env-file .env.production logs --tail 100 server client
sudo systemctl status caddy && sudo journalctl -u caddy -n 50
sudo caddy validate --config /etc/caddy/Caddyfile
```

### Данные

База в томе докера `postgres`, файлы в папке `UPLOADS_HOST_DIR`. Пересборка, перезапуск и откат кода их не трогают. Потерять данные можно ровно тремя способами: `docker compose down -v`, удаление тома или папки руками и `seed:clean`. Ни одна из этих команд в выкатку не входит.

### Резервная копия

```bash
./deploy/backup.sh          # хранит копии 14 дней
./deploy/backup.sh 30       # хранить 30
```

Кладёт в `backups` сжатый дамп базы и архив папки с файлами, старое удаляет само. Папка в гит не попадает. Копия снимается автоматически перед каждой выкаткой, до миграций.

Раз в сутки ночью:

```bash
crontab -e
0 4 * * * cd /srv/diskographia && ./deploy/backup.sh >> backups/cron.log 2>&1
```

Копии лежат на том же диске, что и сайт, поэтому раз в неделю их стоит забирать к себе:

```bash
rsync -avz пользователь@адрес:/srv/diskographia/backups/ ./копии/
```

### Возврат из копии

```bash
./deploy/restore.sh backups/db-2026-09-09_21-00.sql.gz
./deploy/restore.sh backups/db-2026-09-09_21-00.sql.gz backups/uploads-2026-09-09_21-00.tar.gz
```

Стирает текущую базу, создаёт её заново и заливает дамп, спрашивает подтверждение словом «да». Второй аргумент возвращает и файлы.

### Очистка содержимого

```bash
docker compose --env-file .env.production run --rm server pnpm seed:clean --yes
docker compose --env-file .env.production run --rm server pnpm seed:admin
docker compose --env-file .env.production restart server
```

## Демонстрационный режим

`NEXT_PUBLIC_DEMO_MODE=true` закрывает всё служебное от всех, кроме учётки платформы: свои предметы, создание, уведомления, заявки, корзина, настройки, правка учётки, поиск, чужие учётки, сводка и модерация отвечают 404, полосы адресов сверху не видно, вкладка «посетители» у ивента скрыта, ники и теги на страницах не ведут никуда. Наружу торчат только главная, страницы предметов и вход. От индексации демо не закрыто, это намеренно.

Открыть платформу для людей: в переменных репозитория на GitHub поставить `NEXT_PUBLIC_DEMO_MODE=false`, заново запустить сборку образов (Actions, «проверки», Re-run на последнем прогоне `main`), в `.env.production` поставить то же `false` и `REGISTRATION_OPEN=true`, затем `./deploy/deploy.sh`. Ключ вшивается в образ клиента при сборке, поэтому одной правки `.env.production` мало.

## Учётные записи

Набор закрыт: `REGISTRATION_OPEN=false`. Ручка регистрации отвечает отказом, формы на сайте нет, на `/vhod` только вход. Учётки заводит платформа, пока набор не откроют.

Учётка платформы создаётся командой `seed:admin` по `PLATFORM_EMAIL` и `PLATFORM_PASSWORD` из окружения, пароль не короче десяти знаков и без значения по умолчанию. Веса у неё нет, он предельный по определению: флаг `profiles.is_platform`, по нему же сервер и клиент узнают платформу, триггеры её пропускают, на странице учётки вместо числа написано «предельный». Пароль меняется на `/nastroiki`, там же учётка закрывается, оба действия просят пароль.

## Медиа

Файлы прикрепляются к предмету перетаскиванием прямо в экран показа или кнопкой рядом. Что с ними происходит дальше:

- **изображения** идут в обложку и в показ, рядом делается превью в webp
- **аудио** становится предлагаемым сетом: из тегов читаются исполнитель, название и длительность
- **видео и трансляции** youtube и twitch открываются в экране показа, трансляция разворачивается модалкой
- **модель `.glb`** показывается сценой, по которой можно ходить
- **остальные файлы** лежат на полке материалов и скачиваются, ограничений по типу нет

На странице предмета всё, что не картинка, собрано полкой в паспорте, а ссылки предмета прячутся под звёздочкой в нижнем экране.

У глобального ивента показ работает двумя очередями, они настраиваются кнопкой «очереди» и видны только учётке платформы: первая это трансляции и видео, она показывается вместо всего и сама не листается, вторая это фото вместе с вложенными предметами, она крутится по кругу.

Сет всегда один и всегда зациклен. Он не смешивается: включили сет ивента, играет только он. Переход по страницам звук не прерывает.

**Модель из блендера**: File → Export → glTF 2.0, формат **glTF Binary (.glb)**, один файл со всеми текстурами. Скан помещения перед загрузкой стоит уменьшить в полигонах и сжать текстуры, иначе на телефоне он не откроется.

## Шрифты и спрайты

Шрифты лежат в `apps/client/public/fonts`:

- `bd-terminal.woff2` и запасной `bd-terminal.ttf`, вариативный BD Terminal-VF, весь интерфейс
- `ocr-onec.woff2` и запасной `ocr-onec.ttf`, OCR_OneC, читаемые тексты: описания, статьи, манифест

Кегль интерфейса растёт вместе с окном, от 12px на ноутбуке до 17px на 4K, раскладка экранов от этого не меняется.

Спрайты модуля лежат в `apps/client/public/decor`, значок вкладки в `apps/client/src/app`. Всё это кладёт `pnpm assets` из папки с исходниками. Пока шрифтов нет, сайт работает на запасном моноширинном, раскладка от этого не меняется.

## Передача предметов

Заявки на передачу лежат в `entity_transfers`: от кого, кому, состояние, записка. Получатель соглашается сам, на предмет может висеть только одна незакрытая заявка. Ручек и интерфейса пока нет намеренно.

Исключение для платформы: когда она передаёт предмет человеку, вместе с предметом переходит и авторство, и накопленные отклики ложатся в вес получателя. Правило живёт в функции `entity_transfer_apply` в миграции `0011`.
